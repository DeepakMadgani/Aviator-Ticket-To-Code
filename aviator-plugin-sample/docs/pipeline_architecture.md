# Autonomous Ticket-to-Code Pipeline Architecture

This document maps out the complete end-to-end architecture of the LangGraph-based autonomous pipeline that translates an issue ticket into validated, working code. It details the stages, data flow, validation checkpoints, and the information passed between each node.

## High-Level State Flow (The "Memory")
The pipeline operates on a shared state object (the graph state) that is passed from node to node.
**Key data in state includes:**
- `ticket`: The original user request / bug report.
- `workspace_path`: Path to the local repository.
- `discovered_files` & `ranked_files`: Files identified as relevant during evidence collection.
- `evidence_items`: Grounding facts extracted from the codebase to prove relevance.
- `architectural_plan`: The JSON plan generated by the planning agent.
- `blacklisted_files`: Files that failed gating or are locked, fed back to the planner on retries.
- `generated_code` / `build_result` / `test_result`: Execution outputs and validation status.
- `_run_generated_map`: Dict of `{normalized_path: content}` for every file written in the current run — allows later tasks to see the fresh interfaces/models written by earlier tasks.
- `_dataflow_gaps`: Gaps detected by the DataFlow tracer — template bindings with no controller setter.
- `_patch_failures`: Silent generation failures (SEARCH/REPLACE no-ops, cross-service violations, truncation).

---

## Complete Node Execution Order

```
investigate → runtime_diagnosis → unified_analysis
  → discover → hypothesis_investigation → evidence_collection_loop
  → evidence_ranking → semantic_verification → plan → validate_candidates
  → localize → grounded_understanding → ownership_completeness
  → dataflow_verification          ← NEW (data-flow trace before codegen)
  → rag_code → generate_code       ← per-file live compile check inside loop
  → patch_gate → import_validation → angular_module_registration
  → build → [fix_build → build]* → outcome_check → memory_update
```

## 1. Investigation & Requirements Phase
**Nodes:** `investigate_node`, `unified_analysis_node`
* **What happens:** The system ingests the raw ticket. It classifies the intent (e.g., bug fix, feature, refactor), identifies core entities mentioned, and breaks down the implicit requirements.
* **Input:** Raw ticket text.
* **Output:** Structured requirements, initial search terms, and identified technologies.

---

## 2. Evidence Collection Phase
**Node:** `evidence_collection_loop_node`
* **What happens:** The system searches the codebase to ground the ticket in reality. It uses literal search (grepping exact variable names/strings from the ticket), BM25 semantic search, and structural expansion (finding dependencies of found files).
* **Checks:** Filters out locked files, auto-generated files, and test files (unless testing is the goal).
* **Output:** `discovered_files` (a pool of candidate files) and `evidence_items` (specific code snippets proving relevance).

---

## 3. RAG Context Loading Phase
**Nodes:** `rag_code_node`, `rag_test_node`
* **What happens:** The system queries a vector database (Neo4j/Postgres) to find existing architectural patterns, similar past implementations, or testing conventions relevant to the ticket.
* **Input:** The ticket and preliminary evidence.
* **Output:** `code_rag_context` and `test_rag_context` containing snippets of reference code (e.g., "how we normally implement controllers here").

---

## 4. Architectural Planning Phase
**Node:** `plan_node` (Planning Agent)
* **What happens:** An LLM reviews the ticket, the gathered evidence, and the RAG context to output a structured JSON `ArchitecturalPlan`. The plan lists explicit development tasks (`create`, `modify`, `delete`, `read_only`), the files to touch, and the justification.
* **Input:** `ticket`, `evidence_items`, `ranked_files`, `blacklisted_files` (files it must avoid), and `rag_context`.
* **Output:** A proposed `ArchitecturalPlan`.

### Planner System Prompt Rules (enforced on every run)

**DTO / Model co-inclusion rule:** If a task modifies a Service to call a new getter, the DTO/Model that defines that getter must also be a MODIFY task, listed before the service task.

**Angular component co-inclusion rule:** If a task modifies a `*.component.html` to read a new property (`*ngIf="member.isExistingMemberInProject"`), the sibling `*.component.ts` MUST also be a MODIFY task. The `.ts` task must come before the `.html` task. This prevents the planner from generating template bindings with no controller logic to populate them.

**UI data-flow trace rule:** For any ticket that requires displaying new data in the UI, the planner must trace the full path:
1. Backend service/endpoint — does it return the new data? If not, add a task.
2. Frontend service — does it call that endpoint and expose the data? If not, add a task.
3. Component (`.ts`) — does it fetch the data and bind it to a displayed property? If not, add a task.
4. Template (`.html`) — does it render it? Add a task.

A template task showing `{{ member.orgName }}` cannot be planned without corresponding tasks that supply `orgName` at every layer.

---

## 5. Candidate Validation & Gating Phase (The Gatekeeper)
**Node:** `validate_candidates_node` (utilizes `plan_gating.py`)
* **What happens:** This is the critical safety net that intercepts hallucinations and bad architectural decisions before any code is generated.
* **Checks performed:**
  - **Pass 1.5 (Module Boundary Enforcement):** Uses the `ModuleGraph` to verify that proposed dependencies between tasks are legally allowed to import each other.
  - **Pass 2 (Mechanical Prefilter):** Ensures the files exist (if modifying) and aren't blacklisted.
  - **Pass 2.1 (Contextual LLM Judgment):** For `modify` tasks, an LLM checks if the file genuinely contains the logic the planner claims it does.
  - **Pass 2.5 (Architectural Symbol Validation):** A strict boundary check that inspects the actual code symbols the planner intends to use and verifies module import rules.
  - **Consistency Check:** Ensures that if a dependency is rejected, any task relying on it is also rejected.
* **Failure Path:** If tasks are rejected, they are appended to `blacklisted_files`, and the workflow loops back to the **Planning Phase** for a retry (up to 2 times).
* **Output:** A validated, mutated plan containing only `accepted` and `read_only` tasks.

---

## 5a. Companion Co-localization (inside `grounded_understanding_node`)

After the plan is validated, companion files are automatically injected as additional writable tasks. This runs **before** code generation so the code generator has the full file set.

**Forward path (`.ts` → template/style):** When a `*.component.ts` is in the plan, its sibling `*.component.html` and `*.component.scss` are auto-added.

**Reverse path (`.html`/`.scss` → controller) — KEY FIX:** When a `*.component.html` or `*.component.scss` is in the plan, the sibling `*.component.ts` is auto-added via `template_controller_follow` strategy. This ensures that writing a template never happens without the corresponding TypeScript controller logic. Previously only the forward path existed; the reverse path was added after identifying that a planner selecting HTML (for "display as static text" tickets) would miss the `.ts` controller.

**Model import follow:** When a `*.component.ts` imports a model/interface file, that model file is added as a companion so new interface properties are actually declared.

**Type consumer follow:** When a model/interface file is modified, all TypeScript files that import it are added as companions so they receive consistent updates.

## 6. DataFlow Verification Phase — NEW
**Node:** `dataflow_verification_node`
**File:** `src/ticket_to_code/agents/dataflow_tracer.py`

This node implements the **"Read → Think → Verify before Write"** pattern used by Claude Code and Devin. It runs after all plan expansion (`ownership_completeness`) but before RAG and code generation, so missing tasks can be injected in time.

**What it does:**
1. For every HTML task in the plan, reads the existing template file (or session map content).
2. Extracts all Angular template bindings: `*ngIf="x.prop"`, `{{ x.prop }}`, `[attr]="x.prop"`.
3. For each binding, checks whether `prop` is SET anywhere in:
   - The sibling `.ts` controller (direct assignment, object literal, interface declaration)
   - Any model file imported by the controller
   - Other tasks in this run that plan to ADD the property (by reading task descriptions)
4. If a gap is found and the `.ts` controller is **not in the plan** → injects a new MODIFY task automatically with `allowed_methods` set to the exact missing property names.
5. Records all gaps in `state["_dataflow_gaps"]` so `fix_build` knows about them if the build still fails.

**Why this matters:** Without this node, a planner that selected `add-members.component.html` to display `dmember.isExistingMemberInProject` as static text would generate a template binding with no TypeScript logic to populate it. The build passes (TypeScript doesn't check template-bound properties at `tsc --noEmit` level), but the feature is silently broken at runtime.

**DataFlowTracer functions (`dataflow_tracer.py`):**
- `extract_angular_bindings(html)` — parses all `variable.property` bindings from a template
- `extract_property_setters(ts)` — finds all property assignments and interface declarations in a TS file
- `analyze_data_flow(html, ts, models, planned_new_properties)` — core gap analysis returning `DataFlowGap` objects
- `trace_plan_data_flow(plan_tasks, workspace_path, session_map)` — runs analysis across all HTML tasks in the plan

## 7. Code Generation Phase — Extended
**Node:** `generate_code_node`

Tasks are sorted by language tier before generation (topological order):
- Tier 1–3: Java entity → repository → service
- Tier 4–6: TypeScript model → service → component
- Tier 7: HTML templates
- Tier 8: Angular `*.module.ts` (last, after all components it declares are written)

### Session Context Threading (`_run_generated_map`)
Every file written to disk is immediately added to `state["_run_generated_map"]`. Later tasks in the same run inject this map into their generator via `generator._session_files`. This means a component generating after a model sees the **fresh interface shape** — not the on-disk version — preventing type mismatches from stale cached content.

### Post-Write Binding Verification
After writing each HTML file, the generator immediately:
1. Extracts all Angular bindings from the written content.
2. Checks if the sibling `.ts` controller is already in the session map (already written).
   - If yes → verifies each bound property has a setter in the written controller right now.
   - If the controller is in the plan but not yet written → defers check (controller will supply the property).
   - If the controller is neither written nor in the plan → records a `_dataflow_gap` immediately.
3. After writing each `.ts` controller, also cross-checks against any sibling HTML already in the session map.

After writing each `.ts` controller, the generator also checks sibling HTML files already in the session map for missing setters.

### Per-File Live Compile Check (Cursor-style continuous feedback)
After writing **every TypeScript or Java file**, the pipeline runs a fast scoped compile check immediately — before moving to the next file. If errors are found, one inline retry is attempted with the error lines injected into the task description.

**TypeScript files — `_run_tsc_on_files()`:**
- Writes a temporary `tsconfig_aviator_tmp.json` extending the project's `tsconfig.app.json`.
- Overrides `"files"` to only the TypeScript files written so far in this run.
- Runs `npx tsc --noEmit --skipLibCheck -p tsconfig_aviator_tmp.json`.
- `--skipLibCheck` avoids re-checking all `node_modules/*.d.ts` files (saves ~20 seconds).
- Typical runtime: **2–5 seconds** per check.
- Always deletes the temp config in `finally`.

**Java files — `_run_java_compile_on_module()`:**
- Walks up the directory tree from the changed file to find the nearest `pom.xml` or `build.gradle`.
- **Maven modules** (`area-service`, `se-connector-apis`): runs `mvn compile -q --no-transfer-progress`.
- **Gradle modules** (`project-service`, `bim-gateway`, `ene-load-service`, `issues-service`, `sagas-service`): runs `gradlew compileJava --no-daemon -q` (auto-detects `gradlew.bat` wrapper).
- Parses `[ERROR]` lines (Maven) and `error:` lines (Gradle); ignores `[INFO]`/`[WARNING]` noise.
- Gradle daemon stays warm across calls making repeat runs ~10–15 seconds.
- Typical runtime: **15–60 seconds** depending on warm/cold Gradle daemon.

**Inline retry flow (same for both languages):**
```
Write file
  → run scoped compile
  → errors found?
      YES → inject error lines into task.description
           → regenerate THIS file (using broken content as base so LLM sees what to fix)
           → validate retry output
           → write if valid, re-run compile to confirm
           → if still broken → continue to next file (fix_build handles it)
      NO  → continue to next file
```

One retry per file maximum. No infinite loop. `*.spec.ts` and `*Test.java`/`*IT.java` are excluded from live checks (test files compile separately).

### Other Guards in Code Generation
- **Truncation guard:** Rejects output with `[TRUNCATED]`, `...existing code...`, markdown fences embedded in source, Java brace imbalance, Java files not ending with `}`.
- **Export-drop guard:** Rejects TypeScript writes that remove existing `export` statements (prevents TS2305 cascade).
- **Cross-service import guard:** Rejects Java files that import from sibling microservice packages (compile-time classpath violation).
- **Content-unchanged guard:** Detects silent SEARCH/REPLACE failures (patch matched nothing) and triggers full-file fallback.
- **Full-file fallback:** When all SEARCH/REPLACE attempts silently fail, retries the task as a `CREATE` (full file output) before giving up.

## 8. Pre-Build Safety Nodes

### `patch_gate_node`
Runs three deterministic checks on every generated file before the compiler sees them:
1. Scope enforcement — diff must not touch files outside the writable set.
2. Content integrity — no truncation markers or code-fence corruption.
3. Syntax pre-check for known bad patterns.

### `import_validation_node`
Validates that import paths in generated TypeScript files resolve correctly using tsconfig path aliases. Fixes missing or wrong import paths before the compiler runs.

### `angular_module_registration_node`
Ensures any newly created Angular components/directives/pipes are declared in the appropriate `*.module.ts`. Runs after components are written, before build, because Angular's AOT compiler requires all declarations to be registered.

---

## 9. Build & Verification Phase
**Nodes:** `build_node`, `outcome_check_node`

**Build node** runs the full project compiler:
- Angular: `npm run build` (AOT compilation, catches template type errors `ng build` finds that `tsc --noEmit` misses)
- Java: `mvn compile` or `gradle compileJava` for the relevant module
- Parses structured error output to feed `fix_build`

**Outcome check node** runs after a successful build: an LLM reviews the generated code against the original ticket requirements and returns CORRECT / PARTIAL / INCOMPLETE, which is shown in the UI summary.

---

## 10. Fix Loops
**Nodes:** `fix_build_node`, `fix_test_node`

**fix_build receives:**
- Exact compiler error lines with source context (the specific wrong line, not just the file)
- Type definition files for any types mentioned in the error (so LLM knows the correct shape)
- TS2345 property mapping hint — shows source and target types side by side
- `_dataflow_gaps` from the DataFlow tracer — tells fix_build which template bindings need setters in the controller (so it fixes the right file, not the symptom)
- Original pre-modification file contents (to restore accidentally dropped methods)
- STRICT SCOPE LOCK — the LLM is only allowed to fix the specific files the compiler reported errors in

| Companion file discovery | ✅ (bidirectional) | ✅ (both `.ts→html` and `html→.ts`) |
| Data-flow tracing (template bindings) | ✅ | ✅ `dataflow_verification_node` |
| Injects missing tasks mid-run | ✅ | ✅ (dataflow node + companion expansion) |

| Per-file compile feedback + inline retry | ✅ | ✅ (one retry per file, both TS and Java) |
| Multi-cycle fix loops | ✅ (unlimited) | ✅ (up to 5 fix_build cycles) |
| Architectural boundary enforcement | ❌ | ✅ `plan_gating.py`, cross-service import guard |
| Post-build semantic correctness check | ❌ | ✅ `outcome_check_node` |
| Angular module auto-registration | ❌ | ✅ `angular_module_registration_node` |
| Topological task ordering | ❌ | ✅ language-tier sort (Java entity→service→TS model→component→HTML→module) |

## Summary of Node Communication
Each node is a stateless function that receives the `GraphState` dict, performs its localized job, and returns a dictionary of keys to update in the state.
- **Upstream nodes** (Investigation, Evidence) push raw data and context into the state.
- **Midstream nodes** (Planning, DataFlow) synthesize that data into a structured intention with verified data-flow chains.
- **Gating nodes** act as a firewall — reading the intention and either mutating it for safety or forcing a rollback by populating the blacklist.
- **Generation nodes** execute the validated intention file by file, running live compile checks after each write and recording all written content in `_run_generated_map` for cross-file consistency.
- **Downstream nodes** (Build, Fix, OutcomeCheck) run compiler-backed validation and targeted fixes, informed by the DataFlow gap map so they know which properties need setters, not just which lines the compiler complained about.

## 6. Code & Test Generation Phase
**Nodes:** `generate_code_node`, `generate_tests_node`
* **What happens:** Specialist agents take the validated, granular tasks and execute them. The Code Generator writes the implementation, ensuring it adheres to the file's existing structure and the RAG conventions.
* **Input:** The validated `architectural_plan`, existing file contents, and `rag_context`.
* **Output:** Diff strings and file mutations applied to the local workspace.

---

## 7. Build & Verification Phase
**Nodes:** `build_node`, `test_node`, `outcome_verification_node`
* **What happens:** The pipeline attempts to compile/build the project and run the relevant unit tests to verify the code actually works.
* **Checks performed:** 
  - Compilation success.
  - Test suite passes.
  - **Circuit Breaker:** If the build fails, the pipeline tracks the specific error signatures (error codes + symbols). If the pipeline falls into a "stagnation loop" (repeatedly hitting the same error without progress, or introducing net-new unrelated errors), the circuit breaker trips and aborts the workflow to prevent codebase corruption.
* **Output:** Build logs, test logs, and error signatures.

---

## 8. Fix Loops
**Nodes:** `fix_build_node`, `fix_test_node`
* **What happens:** If the build or tests fail, the workflow loops back. A fixer agent reads the compiler/test errors and attempts to patch the code.
* **Input:** The compiler stderr, test logs, and the current codebase state.
* **Output:** New code patches, leading back to the **Build Phase**.
